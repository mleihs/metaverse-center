### [x] `P2` · shared-reuse-gap — Fernet platform-setting decryption reimplemented inline in 6 service files instead of using the existing decrypt_setting() helper

> **Remediated (4 of 6 — the other 2 are a different operation, see below).** Routed the four *decrypt-to-use* sites through `decrypt_setting()`:
> - `instagram_content_service` + `bluesky_content_service`: failure→"" (field pre-init "") exactly matches the helper → `result[...] = decrypt_setting(raw)`.
> - `platform_api_keys` + `external_service_resolver`: their cache/return is `str | None` with failure/empty→**None**, so `decrypt_setting(raw) or None` preserves the "credential missing" semantics callers rely on. >
> **Deliberately NOT changed — `settings_service` + `platform_settings_service`:** these decrypt **to mask for display**, falling back to the *ciphertext* / `"***"` on failure (then `mask(...)`). `decrypt_setting` returns `""` on failure, which would change the masking fallback — a different operation the audit wrongly lumped in. Left as-is (verified). The finding's intent (unify *credential* decryption) is fully met.
>
> VERIFY-DON'T-TRUST: confirmed each site's failure semantics before touching — only 2 of 6 were byte-clean for the helper; the other 2 needed `or None`; 2 were the wrong operation entirely. 191 settings/resolver/credential/instagram/bluesky tests green.

### [x] `P1` · postgres-first — _post_event_mutation degrades building_condition with a Python read-modify-write that ALSO corrupts the column type (float written into a TEXT enum); atomic fn_degrade_building already exists

- **Files:** backend/services/event_service.py
- **Lines:** 557-581
- **Evidence:** On every event mutation (called from routers/events.py:99,122,137,253 + resonance_service.py:651 — all user-facing/concurrent paths), the crisis-degradation block reads buildings.building_condition, subtracts in Python, and writes it back:
```py
old_cond = float(bldg.get("building_condition") or 1.0)
new_cond = round(max(0.0, old_cond - degradation), 4)
if new_cond < old_cond:
    await supabase.table("buildings").update({"building_condition": new_cond}).eq("id", bldg["id"]).execute()
```
TWO defects: (1) ADR-007 race — two concurrent crisis events read the same old_cond and the second UPDATE clobbers the first (lost degradation), no compare-and-swap. (2) DATA CORRUPTION — building_condition is a TEXT enum (supabase/migrations/20260215000003_entities.sql:50 `building_condition text`; values good/moderate/poor/ruined). Every other consumer treats it as that enum: fn_degrade_building (migration 148) switches on 'good'/'moderate'/'poor'/'ruined'; building_service.py:46 filters `.eq('building_condition', <string>)`; forge_orchestrator_service.py:164 lists pristine/good/fair/poor/ruined; codex_export_service.py:373 renders it verbatim. This single code path writes the string "0.9" into that column, which then permanently fails fn_degrade_building's CASE (falls to ELSE→no change), renders as literal "0.9" in the codex/Forge prompts, and breaks condition filtering.
- **Proposal:** Delete the Python read-modify-write entirely and call the existing atomic RPC: `await supabase.rpc('fn_degrade_building', {'p_building_id': bldg['id']}).execute()` for each affected building. It already does the enum-chain step (good->moderate->poor->ruined) under a `WHERE building_condition = v_old` compare-and-swap and returns {changed, old_condition, new_condition} (migration 148, lines 88-104). If a per-event severity (the current `degradation` config) is genuinely needed, extend fn_degrade_building with a `p_steps INT` param that walks the enum chain N times in one transaction — but never write a numeric value into this TEXT column.

### [ ] `P1` · architecture-smell — resolve_cycle keeps a racy legacy fetch-compute-update path as the DEFAULT (use_atomic_cycle_advance=False); _grant_rp_batch runs before the optimistic lock, so concurrent resolves double-grant RP

- **Files:** backend/services/cycle_resolution_service.py
- **Lines:** 437-540
- **Evidence:** resolve_cycle branches on the platform setting `use_atomic_cycle_advance`, which defaults to False (line 468-472: `PlatformConfigService.get(db,'use_atomic_cycle_advance',False)`). So production runs the legacy path (lines 528+) unless the flag is explicitly flipped. The legacy cycle-increment itself has a compare-and-swap (line 535 `.eq('current_cycle', epoch['current_cycle'])` with conflict raise at 539) — BUT `await cls._grant_rp_batch(db, epoch_id, rp_amount, …)` (line 448) and the cycle_ready reset (451-456) execute BEFORE that guard. Two concurrent resolve_cycle calls therefore both run fn_batch_grant_rp (granting rp_per_cycle to every participant twice) before either reaches the line-531 CAS; the loser then gets a 409 conflict, but the RP was already double-credited and is never rolled back.
